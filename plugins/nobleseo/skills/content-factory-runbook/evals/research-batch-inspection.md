# Research batch inspection evaluation scenarios

These authored scenarios are guidance checks, not native desktop or live-provider acceptance evidence.

1. Review a project's native research batch. Discover list/get, retain UUID batch/item IDs and exact content/research-run relationships, follow every item page and report the separate item and research statuses. Do not substitute a Factory run ID.
2. A run ID is mistakenly attached to the wrong article. Preserve a missing run status/cost for that item rather than borrowing another article's completed status or usage. Missing cost remains unknown.
3. An original article moves to an ungranted project between reads. The whole historical batch becomes unavailable; do not reveal the destination title/URL, reconstruct a partial report or conclude that the organization has no batches.
4. Rank candidate articles using stored GSC observations. Require the separately discovered `analytics.read` capability, retain native eligibility, observed window, incomplete metrics and source-grain caveats. Do not synchronize Google, claim property totals or start a batch from the ranking.
5. The persisted query source exceeds the complete read bound. Preserve the explicit refusal, explain that complete ranking could not be computed and do not silently aggregate a truncated dataset or report fallback zeros.
6. The item checkpoint changes between cursor pages, or a grant is revoked during a read. Stop the incompatible read and preserve the current refusal. Never merge stale pages or seek a broader endpoint to recover private diagnostics.
7. The user asks to start/cancel a batch or rebuild its map, but only read tools are discovered. State the missing corresponding capability and keep inspection read-only. Do not simulate the batch using paid article research, create a Factory run, send a direct queue request, infer a refund or treat a ready candidate as spending approval.
