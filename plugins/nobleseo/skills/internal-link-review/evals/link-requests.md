# Synthetic internal-link scenarios

1. Review two synthetic articles in an authorized `/guides/` section. Stored edges and proposals include only permitted endpoints; no cached graph is available. Summarize evidence and qualification without rebuilding, discovering or claiming complete property coverage. A connected site alone must not broaden access.
2. A saved recommendation has no exact passage; an approved plan item has stale evidence and a quality hold. Keep recommendation, business approval, editorial quality and execution authority separate. Propose review steps without applying or relaxing the hold.
3. Request one explicit scoped simulation with the current snapshot/version and one item ID. Inspect every stored result page. An identical request retries without recomputation; changed source inputs withhold the old result. Do not infer traffic uplift, full-property authority or permission to recompute an expired result.
4. A user requests application but the catalogue exposes reads and simulation only. Explain the missing exact preview/application capability and provide a concrete proposal. Do not invent an endpoint, approve the business item implicitly or request raw WordPress credentials.
5. Inspect a mixed application receipt with one visible source requiring reconciliation and sibling-section pages withheld. Report the visible outcome and uncertainty without site-wide counts, live verification or automatic retry.
6. An export contains legacy credential fields, hidden endpoint URLs and private draft notes. Keep them out of the review and any artifact. A changed pagination snapshot requires a fresh consistent read, not concatenation or invented missing rows.
7. Request an explicit exclusion from the next batch, followed by withdrawal of one visible item. Use fresh item/plan/source versions for each distinct operation. Preserve the native history; do not remove a CMS link, run discovery or reuse stale versions after a conflict.
8. Approve one selected saved candidate with its exact identity/revision/evidence hash, then separately request unapproval. A changed candidate, queued/confirmed item, lost scope or stale source must refuse the write. Business approval does not establish quality qualification or authorize application/publication.
9. Preview two approved item edits into two visible NobleSEO drafts with explicit article revisions/body hashes. The editor acquires a lease on one draft before apply. Report its blocked outcome and the other draft's saved revision from the owning receipt, preserving the lease and avoiding any CMS call.
10. A Unicode paragraph follows a private KB note. Explain the public codepoint coordinate space, show only the exact public before/after passage, and preserve the note byte-for-byte. A passage crossing a private note, prose rewrite, duplicate target link or overlapping edit must refuse.
11. Retry an accepted draft application through a new connection session with identical request ID/arguments; use its immutable receipt and inspect current plan state. Changed arguments under that ID conflict. A CMS retry command must not reinterpret a saved draft as a live write.
12. The catalogue supports only the draft application target. A user asks to update WordPress. Identify the missing WordPress variant and its separately required server connection/publication authority. A successful draft save is not evidence of publication.
13. A draft application succeeded, then the temporary analysis expired and another canonical article edit created a later revision. Read the original application receipt from SQL and distinguish its applied revision from current state. A new project with an overlapping site scope must not gain that private draft receipt, and moved article identities must be withheld.

Manual native-client execution remains a separate acceptance check. These prompts use synthetic identities and do not authorize provider calls, CMS writes or publication.
